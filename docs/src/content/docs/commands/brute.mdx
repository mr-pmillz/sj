---
title: brute
description: Discover hidden Swagger/OpenAPI definition files by brute-forcing common paths.
---

The `brute` command sends requests to a target host to discover Swagger/OpenAPI definition files at commonly used paths. This is useful when you suspect a target exposes an API but do not know where the definition file is located.

## Usage

```bash
sj brute -u <URL> [flags]
sj brute -U <FILE> [flags]
```

## Flags

In addition to the [global flags](/commands/global-flags/), `brute` accepts:

| Flag | Short | Default | Description |
|------|-------|---------|-------------|
| `--wordlist` | `-w` | *(built-in)* | Path to a custom wordlist of paths to brute-force. |
| `--endpoint-only` | `-e` | `false` | Only print the discovered endpoint path (no extra output). |
| `--output-format` | `-F` | `console` | Output format: `console`, `json`, `jsonl`, `csv`, or `txt`. |
| `--output-all-formats` | `-O` | `false` | Write JSON, JSONL, CSV, and TXT outputs. Requires `-o`. |
| `--url-file` | `-U` | | File containing a list of target URLs to brute-force (one per line). |
| `--max-candidates` | | `10000` | Bound generated URLs or batch targets. |
| `--workers` | | `1` | Number of target URLs scanned concurrently in batch mode. |

## Examples

### Basic brute-force

```bash
sj brute -u https://target.example.com
```

### With a custom wordlist

```bash
sj brute -u https://target.example.com -w /path/to/wordlist.txt
```

### Endpoint-only output

```bash
sj brute -u https://target.example.com -e
```

### Batch mode with a URL file

```bash
sj brute -U urls.txt
```

Where `urls.txt` contains one target URL per line:

```text
https://target1.example.com
https://target2.example.com
https://target3.example.com
```

### JSON output

```bash
sj brute -u https://target.example.com -F json -o brute-results.json
```

### Through a proxy

```bash
sj brute -u https://target.example.com -p http://127.0.0.1:8080
```

## How It Works

1. A prioritized list of common specification and documentation-UI paths is loaded from the built-in list or a custom wordlist.
2. Bounded responses are content-sniffed to find Swagger 2.0 or OpenAPI 3.x documents even when the server labels them incorrectly.
3. Swagger UI, Redoc, and Swashbuckle references are followed through HTML, initializer JavaScript, and JSON configuration documents. Discovered references are promoted ahead of the remaining bulk candidates.
4. Reference traversal is limited to the original HTTP(S) origin, three reference hops, 32 references per response, and the configured overall candidate limit. Cross-origin, credential-bearing, and non-HTTP references are rejected before a request is sent.
5. Browser/WAF challenge pages are classified separately from transport errors and ordinary HTTP responses.
6. Discovered definition files and coverage limits are reported. In batch mode (`-U`), a combined summary is printed after all targets are processed.

JSON summaries expose `waf_challenge_detected`, `waf_challenge_responses`, `references_rejected`, and `references_skipped`. These fields are also stored in SQLite runs and included in generated assessment reports so a challenge or traversal limit is not mistaken for complete negative coverage.

:::caution
Custom request headers are applied to same-origin references only. If an authorized target requires a solved browser session, use the exact browser User-Agent and Cookie headers from the same network path. Treat session cookies and JSON result files containing authenticated specification URLs as sensitive assessment data.
:::

:::tip
Combine `brute` with `automate` for a complete workflow. JSON and JSONL discovery output can be passed directly to `automate`, including reports from batch brute-force runs.

```bash
# Step 1: Discover definition files
sj brute -U targets.txt -F json -o discovered.json

# Step 2: Scan every discovered specification
sj automate -U discovered.json -F json -o scan-results.json
```
:::
